Running the pick-and-place demo

Visualises the full pipeline on a Franka Panda in RViz 2 and Gazebo, with the same generated object that was scored in Table II.

What you will see

  • Gazebo (left half of screen). The generated object rests on a table in the panda_eval_world. The Panda itself is not in Gazebo — only the object — so the gz window shows the object physics. (Adding the Panda to Gazebo is on the roadmap.)
  • RViz 2 (right half of screen). The Panda's RobotModel display animates through a full pick-and-place sequence: ready → pre-grasp → grasp → lift → transport → place → retract → ready. While the object is "grasped" a marker travels with the gripper. Each stage's joint trajectory is computed by MoveIt 2 (RRTConnect via OMPL).

Prerequisites

Same as Reproduce, plus a display server. Run the workspace build first if you haven't already:

cd ros2_ws
source /opt/ros/jazzy/setup.bash
colcon build --packages-select generated_objects_eval
source install/setup.bash
cd ..

You also need a generated manifest to drive the demo (see step 1 of Reproduce if you haven't built one):

python3 scripts/build_eval_manifest.py \
    --budget 1500 --top-k 25 --seed 42 \
    --out output/seed_42/eval_manifest.json
python3 scripts/patch_sdf_collision.py \
    --manifest output/seed_42/eval_manifest.json

Launch the demo

1 Full pick-and-place with physics (recommended)

ros2 launch generated_objects_eval visual_demo.launch.py use_gz_control:=true

The launch picks output/seed_42/eval_manifest.json automatically; pass manifest:=/abs/path/eval_manifest.json to point elsewhere. What this brings up:

  1. gz sim -r on panda_eval_world; the Panda is spawned from /robot_description via ros_gz_sim create.
  2. gz_ros2_control inside gz brings up the controller_manager; spawners activate joint_state_broadcaster, panda_arm_controller (JointTrajectoryController), and panda_hand_controller.
  3. robot_state_publisher + a static world → panda_link0 TF.
  4. rviz2 with the bundled demo.rviz (RobotModel + Marker displays).
  5. demo_plan_driver: shuffles the manifest, spawns one random object in gz, publishes the table as a CollisionObject on /planning_scene so RRTConnect plans around it, then on each cycle plans the 8-stage pick-and-place and hands the trajectory to panda_arm_controller via MoveItPy.execute(). Every full pass through the pool is re-shuffled.

Pin a specific object with --object-index N (Argument lookup: search the manifest's name field) or fix the shuffle with --seed K. Stop with Ctrl-C.

2 RViz-only animation (no physics)

ros2 launch generated_objects_eval visual_demo.launch.py

Same driver, but use_gz_control:=false (default) so the planned trajectory is animated directly on /joint_states; faster on slow GPUs and what's recorded as rviz_motion_plan.mp4 on the project page.

Just Gazebo (drop & settle)

# Terminal A: world
ros2 launch generated_objects_eval stability_world_gui.launch.py

# Terminal B: run the stability eval with a small N (so you can record a clip)
ros2 run generated_objects_eval gazebo_stability_eval \
    --manifest $(pwd)/output/seed_42/eval_manifest.json \
    --out /tmp/gz_video.json --max-objects 6

The eval node spawns each object, lets physics settle for 2.5 s, then despawns. Good for a 30 s clip of the drop+settle behaviour.

Archetype tour video

# Boot Gazebo (windowed)

Recording the videos

Option A — ffmpeg + x11grab

WIN=$(xdotool search --name "Gazebo" | head -1)
xdotool getwindowgeometry $WIN          # note position + size

ffmpeg -f x11grab -framerate 30 -video_size 1280x720 -i :0.0+100,80 \
       -c:v libx264 -pix_fmt yuv420p -crf 23 \
       docs/videos/gz_drop_settle.mp4

Stop with Ctrl-C. Repeat for the RViz window or capture the whole screen for the side-by-side video.

Option B — OBS Studio

Add one Window Capture source per pane (Gazebo, RViz), arrange into a side-by-side scene, set the output to mp4, hit Start Recording, then run the launch file.

Option C — Gazebo's built-in recorder

In the gz sim window: Settings → Video Recording → Start. Saves to ~/.gz/sim/videos/. Useful only for the Gazebo half; doesn't capture RViz.

Drop the resulting mp4 files into docs/videos/ with the names below; the project-page index wires those filenames into the four video cards:

Common gotchas

RViz starts but the Panda doesn't render

  • Confirm /joint_states is being published: ros2 topic echo /joint_states --once.
  • Confirm the static world → panda_link0 TF is up: ros2 topic echo /tf_static --once.
  • If RViz Fixed Frame still complains, change it to panda_link0 via Displays → Global Options.

NVIDIA libEGL warnings — failed to create dri2 screen

On hybrid-graphics laptops (NVIDIA Optimus / Prime), gz_sim picks the wrong renderer. Try one of:

# a) Force gz to render through the NVIDIA GPU
__NV_PRIME_RENDER_OFFLOAD=1 __GLX_VENDOR_LIBRARY_NAME=nvidia \
ros2 launch generated_objects_eval visual_demo.launch.py manifest:=...

# b) Or force gz to use the OGRE 1.x renderer (no Vulkan/EGL needed)
ros2 launch generated_objects_eval visual_demo.launch.py manifest:=... \
    --ros-args -p render_engine:=ogre

# c) Or run gz with software rendering (slow but always works)
LIBGL_ALWAYS_SOFTWARE=1 ros2 launch generated_objects_eval visual_demo.launch.py manifest:=...

The bundled launch file uses OGRE2; if you don't have a working OGRE2 install, edit launch/visual_demo.launch.py and remove the --render-engine ogre2 flag from the gz sim command.

"Missing virtual_joint" warning every second

The Panda SRDF declares a virtual_joint linking world to panda_link0; until the static TF is published, MoveIt's planning_scene_monitor will log this warning. Our launch file starts static_transform_publisher automatically; if you see the warning, that node failed to start (check ~/.ros/log/*/static_transform_publisher*.log).

CheckStartStateCollision' failed in the planning log

The Panda is being evaluated at all-zero joints, which puts it in self-collision. The demo_plan_driver uses arm.set_start_state(configuration_name="ready") (the SRDF group state); if you see this error, an older binary is being executed — rebuild with colcon build --packages-select generated_objects_eval.

Stale gz sim instances from a previous run

gz transport advertises services by world name, so two server instances on panda_eval_world route service calls non-deterministically. Kill them before each run:

pkill -KILL -f "gz sim"
pkill -KILL -f "gazebo_stability_eval"
pkill -KILL -f "moveit_planning_eval"
